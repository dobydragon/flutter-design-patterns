Design Patterns — Interview Questions (Junior → Senior)

الإجابات بالإنجليزي (زي ما هتقولها في الـ interview)، وتحتها الفكرة بالمصري.
لما يكون عندك مثال من مشروعك، استخدمه. الأمثلة من كودك بتفرق جداً عن الإجابات المحفوظة.

🟢 Junior

J1 What is a design pattern?

Answer: A reusable, named solution to a recurring design problem. It's not code you copy; it's a structure you adapt. Patterns also give the team a shared vocabulary: saying "this is a Facade" explains a lot in one word.

الفكرة: حل متكرر لمشكلة متكررة، ليه اسم عشان الناس تتفاهم بسرعة. مش library.

J2 Design pattern vs architecture?

Answer: A design pattern solves a local problem between a few classes, like Strategy or Adapter. Architecture defines how the whole app is split into layers and how they depend on each other, like MVVM or Clean Architecture. One architecture usually contains many design patterns.

الفكرة: الـ pattern = أوضة. الـ architecture = تقسيم الشقة كلها.

J3 What is a Singleton and give a Flutter example?

Answer: A class with exactly one instance and a global access point. For example, a CacheHelper with a private constructor and a static final instance, so the whole app shares one SharedPreferences wrapper. Firebase also uses this: FirebaseAuth.instance.

الفكرة: نسخة واحدة. ذكر مثال حقيقي زي CacheHelper._() بيوري إنك كتبته فعلاً.

J4 What's a factory constructor in Dart?

Answer: A constructor marked factory that doesn't have to create a new instance. It can return a cached instance, a subtype, or run logic first. It's common for parsing, for example UserProfileModel.fromFirestore(...), and for ServerFailure.fromCode(code), which picks the right message key from an error code.

الفكرة: constructor بيقدر يقرر هيرجع إيه.

J5 What is the Observer pattern? Where is it in Flutter?

Answer: A subject notifies all subscribers when its state changes. In Flutter it's everywhere: Stream, ChangeNotifier, and BLoC. In a typical app, Cubits listen to Firestore snapshots() streams and emit new states, and BlocBuilder rebuilds the UI.

الفكرة: push بدل polling.

J6 Why should UI not call Firebase directly?

Answer: It mixes rendering with data access, makes the UI hard to test, and spreads Firebase details everywhere. A good rule is that UI never imports firebase_auth; it goes through AuthService, and data goes Screen → Cubit → Service.

الفكرة: فصل المسؤوليات.

J7 What is copyWith and why do states use it?

Answer: It returns a new object with some fields changed, keeping the old one immutable. Immutable states plus value equality (Equatable) let BLoC detect real changes and avoid unnecessary rebuilds.

الفكرة: ما تعدلش في الـ state، اعمل نسخة جديدة.

🟡 Mid-level

M1 Explain Dependency Injection and how you did it in Flutter.

Answer: A class receives its dependencies instead of creating them. Every service and Cubit takes its dependencies in the constructor. All services are created once in a composition root (a MultiRepositoryProvider at the top of the app), and screens read them with context.read and pass them to their Cubit. Services take an optional FirebaseFirestore, so in tests I pass FakeFirebaseFirestore.

الفكرة: 3 حاجات: constructor injection، composition root، testability. وقول مثال الـ test.

M2 DI vs Service Locator?

Answer: With DI, dependencies are pushed in and visible in the constructor. With a Service Locator, the class pulls them from a global registry, like getIt<T>(), so they're hidden and fail at runtime if not registered. context.read<T>() is technically a lookup, so I keep it at the edge, in Screen.builder(), and inject into the Cubit. That way the Cubit stays pure and testable.

الفكرة: push vs pull. والحل الوسط.

M3 What is the Repository pattern? Is a class called "Repository" enough?

Answer: No. A repository is a boundary that gives the rest of the app a collection-like API in domain terms and hides where data comes from: remote, cache, or local. It should own mapping and the caching policy, and ideally sit behind an interface. A real repository means Cubits only talk to it, and it combines its sources (for example a Firestore source, an access-rules check and a user lookup) and verifies the write. If Cubits call a Firestore service directly, that service is acting as data source and repository at once.

الفكرة: الاسم مش دليل. الدليل: مين بيكلمه، وبيخبي إيه.

M4 Repository vs Data Source vs Service?

Answer:

  • Data source: talks to one backend; raw I/O.
  • Repository: combines data sources, maps to models, and owns caching and the source of truth.
  • Service: often a wrapper around an external SDK, or a stateless operation like notifications.

The Flutter architecture guide uses "services" for the lowest layer that wraps APIs, and "repositories" above them.

الفكرة: Data source = سلك. Repository = مدير البيانات. Service = أداة.

M5 What is a Facade? Example?

Answer: A simple interface in front of a complex subsystem. A NetworkManager can hide connectivity_plus, an internet checker, Dio, timers and a retry queue behind canMakeRequests, statusStream and retryConnection(). A common weakness: an AuthService that still returns Firebase's UserCredential simplifies but doesn't fully isolate the SDK.

الفكرة: لو ذكرت عيب في كودك، ده بيوري نضج.

M6 Strategy vs if/else?

Answer: Strategy turns each algorithm into an object, or a function in Dart, so you can add one without editing the others (Open/Closed). With 2–3 fixed cases, a switch on an enum is simpler and clearer. For example, an AppNavigator can use Navigator on mobile and a go_router function injected by the web build.

الفكرة: Strategy لما الحالات بتزيد أو بتتبدل وقت التشغيل.

M7 How do you handle errors between layers?

Answer: A common setup: services throw, Cubits catch and map with one ErrorHandler.handle(e) into a typed Failure with a user-safe message, then emit an error state. The improvement is returning a sealed Result<T> from repositories, so the compiler forces callers to handle failure.

الفكرة: الوضع الحالي + التحسين.

M8 MVVM in Flutter: what's the ViewModel?

Answer: The Cubit or ChangeNotifier holding UI state and logic; the View observes it. Rules: the View has no business logic, and the ViewModel has no widgets. A common mistake is a TextEditingController stored inside a Cubit state; that's a UI object leaking into the ViewModel.

الفكرة: View بيعرض، ViewModel بيقرر.

M9 Is using BLoC the same as using Clean Architecture?

Answer: No. BLoC is a state-management approach for the presentation layer. Clean Architecture is about dependency direction: domain in the center with entities and use cases, and data and UI depending on it through interfaces. You can use BLoC without Clean, and many apps do.

الفكرة: سؤال فخ مشهور.

🔴 Senior

S1 When is a Singleton harmful?

Answer: When it holds mutable global state accessed directly via .instance: hidden dependencies, order-of-initialization bugs, and tests that leak state into each other. I prefer a "soft singleton": a public constructor for tests, plus one instance created in the composition root and injected. A network manager is a good candidate for this.

الفكرة: المشكلة مش "نسخة واحدة"، المشكلة "وصول global".

S2 Design an offline-first attendance check-in.

Answer (outline):

  • UI → CheckInCubit (ViewModel)
  • → AttendanceRepository (interface), backed by a local store (source of truth) and a remote data source.
  • Writes go local first and enter a Command queue (each check-in is an object with an id for idempotency), flushed on reconnect.
  • Strategy for the verification method (GPS/QR/Wi-Fi).
  • Result types for failures.
  • An Observer stream exposes pending/synced status.
  • Server-side dedupe by command id.
  • Trade-off: if using Firestore, its offline persistence already queues writes, so a custom queue may duplicate it.

الفكرة: وريه إنك بتختار pattern لكل مشكلة، وإنك عارف امتى ما تستخدموش.

S3 How would you migrate a large "Cubit → Service" codebase toward Clean Architecture without a rewrite?

Answer: Incrementally.

  1. Introduce interfaces for the most-tested or most-changing services.
  2. Add repositories per feature as Cubits get touched (strangler pattern).
  3. Fix dependency direction: core must not import features, and break package cycles by extracting shared models.
  4. Add Result at repository boundaries.
  5. Add use cases only where there's real cross-repository business logic.

Measure progress by Cubits testable with fakes.

الفكرة: تدريجي، والـ use case مش لكل حاجة.

S4 Decorator vs inheritance for adding caching?

Answer: Inheritance fixes the combination at compile time and leads to class explosion (CachedLogged…). A Decorator wraps any implementation of the same interface, so you compose caching, logging and retry in the composition root and test each one alone. It requires an interface, which is another reason to introduce abstractions.

S5 Command pattern in Flutter's official architecture — why?

Answer: Flutter's docs wrap ViewModel actions in Command objects that expose running, error and completed state. The UI can then show loading and errors per action without ad-hoc booleans in the state. It also composes with Result.

مصدر: https://docs.flutter.dev/app-architecture/design-patterns/command

S6 What would you change first in your own project's architecture?

Answer:

  1. Break any package cycles and core→features imports.
  2. Introduce interfaces for the main data services so Cubits can be unit-tested with fakes.
  3. Split very large services by responsibility.
  4. Return Result instead of throwing.

I'd do it incrementally while touching features, not as a big rewrite.

الفكرة: نقد ذاتي واقعي = إشارة Senior قوية.

S7 Abstract Factory — when would you actually use it in Flutter?

Answer: Rarely. It's for creating families of related objects that must match, like a full Cupertino vs Material widget set, or a white-label app where each brand needs a matching set of services. Usually theming and Platform checks are enough. I'd mention it's a pattern I understand but haven't needed.

الفكرة: الصراحة إنك ما استخدمتوش أحسن من إنك تخترع.
