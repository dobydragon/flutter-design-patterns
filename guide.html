الجزء الأول — الأنماط الأساسية

1 Dependency Injection

1. ما هو؟
الـ class ما بيعملش الحاجات اللي محتاجها بنفسه. بتيجيله جاهزة من برة، غالباً في الـ constructor.

2. ليه اتعمل؟
عشان الـ classes كانت مربوطة ببعض جامد (tight coupling). لو A بيعمل new B() جواه، مستحيل تبدّل B من غير ما تعدّل A.

3. المشكلة اللي بيحلها

  • قبل: AttendanceService بيعمل SystemClock() جواه، فمش هتقدر تختبر "الموظف متأخر؟" من غير ما تستنى الساعة 9.
  • بعد: AttendanceService(clock: FixedClock(09:15))، والاختبار بيدي نفس النتيجة كل مرة.

4. بيشتغل إزاي؟

  1. الـ class بيعلن احتياجاته في الـ constructor.
  2. فيه مكان واحد اسمه Composition Root بيعمل كل الـ objects ويوصلهم ببعض.
  3. في الـ test بتبعت نسخ fake.

أنواعه: constructor injection (الأشهر)، setter injection، method injection.

5. ليه في Flutter؟

  • Testing بـ fakes.
  • تبديل Firebase بـ emulator أو fake.
  • Provider و RepositoryProvider و get_it (الأخير بيُستخدم كـ locator).

6. امتى تستخدمه؟

  • مناسب: أي class بيكلم I/O (network, DB, time, storage) أو محتاج تختبره.
  • زيادة: value objects، helpers نقية، widgets بسيطة.

7. عيوبه

  • Composition root ممكن يكبر جداً (عشرات الـ providers في app كبير).
  • Constructors طويلة (Cubit بياخد 5–6 dependencies).
  • لو من غير interfaces، القيمة نصها بس.

8. في الـ Interview

EN: "Dependency Injection means a class receives its dependencies instead of creating them. In Flutter I use constructor injection everywhere, with a single composition root built from MultiRepositoryProvider at the top of the app. Services take an optional FirebaseFirestore, so in tests I inject FakeFirebaseFirestore. The benefit is loose coupling and testability."

بالمصري: "الـ class ما بيعملش حاجاته، بتيجيله. أنا بعمل كل الـ services في مكان واحد وبوزعها بـ Provider، وعشان كده قدرت أختبر الـ services بـ Firestore وهمي."

9. أسئلة متابعة

  • Q: Is Provider DI or Service Locator? → A: The tree-scoped providers are DI-like, but context.read<T>() is a lookup. I use it only at the edge, in Screen.builder, then inject into the Cubit.
  • Q: Why constructor injection over setter? → A: The object is always valid after construction, dependencies are visible, and fields can be final.
  • Q: What would you improve? → A: Interfaces for key services, and removing the duplicate instances.

2 Observer

1. ما هو؟
Object (Subject) بيبلغ كل المشتركين (Observers) أول ما حالته تتغير.

2. ليه اتعمل؟
عشان أجزاء كتير تعرف بالتغيير من غير ما تكون مربوطة ببعض ومن غير polling.

3. المشكلة

  • قبل: الشاشة بتسأل كل ثانية "فيه check-in جديد؟"، وده شغل على الفاضي وتأخير.
  • بعد: المصدر بيبعت لما يحصل تغيير بس.

4. بيشتغل إزاي؟

  1. Subject عنده list of listeners.
  2. subscribe / unsubscribe.
  3. لما يتغير: notify الكل.

في Dart: Stream + listen + StreamSubscription.cancel().

5. ليه في Flutter؟

  • Flutter كله reactive: Stream, ChangeNotifier, ValueNotifier, Bloc/Cubit.
  • Firestore snapshots() = observer جاهز.

6. امتى؟

  • مناسب: بيانات live، حالة الشبكة، auth state، notifications counter.
  • زيادة: قيمة بتتقرا مرة واحدة. استخدم Future.

7. عيوبه

  • Memory leaks لو نسيت cancel.
  • ترتيب الإشعارات مش مضمون.
  • صعب تتبع "مين غيّر إيه" لو الـ observers كتير.
  • StreamBuilder اللي بيقرا من Firestore مباشرة في الـ UI بيتخطى الـ Cubit.

8. Interview

EN: "Observer lets a subject notify subscribers when its state changes. In Flutter it's built into Streams and BLoC. In a typical Cubit setup, Cubits subscribe to Firestore snapshot streams and emit new states, and the UI observes the Cubit through BlocBuilder. I always cancel subscriptions in the Cubit's close() to avoid leaks."

بالمصري: "اللي عنده البيانات بيبلغ اللي مهتمين. Firestore بيبلغ الـ Cubit، والـ Cubit بيبلغ الشاشة، وبقفل الاشتراك لما الشاشة تتقفل."

9. أسئلة متابعة

  • Q: Single-subscription vs broadcast stream? → A: Single allows one listener and buffers events. Broadcast allows many and doesn't buffer for late listeners.
  • Q: How do you avoid leaks? → A: Keep the StreamSubscription, cancel it in close() or dispose(), and check isClosed before emitting.
  • Q: BlocListener vs BlocBuilder? → A: Builder rebuilds UI. Listener runs side effects once per state (navigation, toast).

مصادر: Observer · Dart Streams

3 Facade

1. ما هو؟
واجهة بسيطة قدام نظام معقد.

2. ليه اتعمل؟
عشان الـ client ما يحتاجش يعرف 5 classes وترتيب استدعائهم.

3. المشكلة

  • قبل: شاشة الـ Login بتنادي FirebaseAuth، وبعدين FCM، وبعدين Firestore، وبتترجم error codes بنفسها.
  • بعد: authService.signIn(...).

4. بيشتغل إزاي؟
Class بيمسك references للـ subsystems، وبيقدم methods قليلة عالية المستوى، وبيفوّض للداخل.

5. ليه في Flutter؟

  • Firebase SDKs كتير ومعقدة.
  • لو غيرت SDK، بتعدل مكان واحد.
  • بتمنع الـ UI من الـ imports المباشرة.

6. امتى؟

  • مناسب: SDK معقد أو أكتر من subsystem بيتنادوا مع بعض.
  • زيادة: call واحدة بسيطة.

7. عيوبه

  • ممكن يبقى God object لو كبر (network manager بـ مئات السطور).
  • لو بيسرّب types الـ SDK، العزل ناقص.

8. Interview

EN: "A Facade gives a simple interface to a complex subsystem. For example, an AuthService wraps Firebase Auth, and the rule is that UI never imports firebase_auth directly. A NetworkManager can hide connectivity checks, an internet checker, Dio and a retry queue behind a few methods. A common limitation is returning Firebase's UserCredential from the facade. Returning your own AppUser fully isolates the SDK."

بالمصري: "واجهة بسيطة قدام حاجة معقدة. واعرف عيبها: لو سرّبت types الـ SDK، العزل ناقص."

9. أسئلة متابعة

  • Q: Facade vs Adapter? → A: Facade simplifies many classes. Adapter converts one interface to another expected one.
  • Q: Facade vs Repository? → A: A repository is a facade specialized for data, with a domain API, mapping and caching.

4 Singleton

1. ما هو؟
Class ليه نسخة واحدة بس ونقطة وصول global.

2. ليه اتعمل؟
موارد مشتركة غالية أو لازم تبقى واحدة: config، cache، connection pool.

3. المشكلة

  • قبل: كل شاشة بتعمل storage object جديد، فالبيانات مش متسقة والـ init بيتكرر.
  • بعد: LocalStorage.instance.

4. بيشتغل إزاي؟

  1. Private constructor ClassName._().
  2. static final instance (eager)، أو static X? _instance + ??= (lazy).
  3. (اختياري) factory ClassName() => instance;.

5. ليه في Flutter؟

  • SharedPreferences wrapper.
  • Firebase نفسه (FirebaseAuth.instance).
  • Logger.

6. امتى؟

  • مناسب: resource واحد فعلاً (cache, logger, connectivity monitor).
  • زيادة: حاجة ملهاش state (استخدم static أو top-level functions)، أو حاجة محتاج نسخ مختلفة منها في الـ tests.

7. عيوبه

  • Global mutable state.
  • Hidden dependencies (X.instance جوه أي method).
  • Tests بتأثر على بعض.
  • ترتيب init: wrapper زي CacheHelper بيرمي StateError لو نسيت init().

8. Interview

EN: "Singleton guarantees one instance with a global access point. A typical use is a SharedPreferences wrapper with a private constructor and a static instance. But I prefer not to access singletons directly inside business classes. For something like a network manager, keep the constructor public for tests and inject the shared instance through Provider. That keeps the single instance without hiding the dependency."

بالمصري: "نسخة واحدة، بس بوزعها بالـ DI بدل ما أناديها من أي حتة."

9. أسئلة متابعة

  • Q: Is a Singleton an anti-pattern? → A: Only when used as hidden global state. A single instance managed by the DI container is fine.
  • Q: Lazy vs eager in Dart? → A: Dart static final fields are already lazily initialized on first access. ??= is explicit laziness.
  • Q: Thread safety? → A: Dart isolates don't share memory, so the classic double-checked locking isn't needed. Each isolate gets its own instance.

5 Factory (Simple Factory / Factory Constructor)

1. ما هو؟
مكان واحد (method أو constructor) بيقرر إزاي يتعمل الـ object. الـ caller بيطلب بس.

تنبيه: ده مش GoF Factory Method (ده بيعتمد على inheritance، وشرحه في الجزء التالت).

2. ليه اتعمل؟
عشان منطق الإنشاء ما يتكررش ويتلخبط في كل مكان.

3. المشكلة

  • قبل: كل شاشة بتبني notification بإيدها، فبيحصل typo في الـ route.
  • بعد: AppNotification.forKind(kind).

4. بيشتغل إزاي؟

  • factory constructor في Dart ممكن يرجّع subtype أو cached instance أو يعمل logic.
  • أو static method بيرجّع object.

5. ليه في Flutter؟

  • fromJson و fromFirestore.
  • اختيار widget أو notification أو failure حسب نوع.

6. امتى؟

  • مناسب: إنشاء فيه قرار (نوع، fallback، parsing).
  • زيادة: Point(x, y).

7. عيوبه

  • switch كبير بيكبر مع كل نوع جديد. لو كبر جداً، فكّر في registry أو Strategy.

8. Interview

EN: "A factory centralizes object creation. In Dart I use factory constructors like fromFirestore for parsing, and Failure.fromCode, which maps a backend error code to the right message key. For notifications, a NotificationTemplate.forKind factory can build the title, body and route for each type, with a fallback when localization isn't loaded."

بالمصري: "مكان واحد بيقرر إزاي الحاجة تتعمل."

9. أسئلة متابعة

  • Q: factory constructor vs static method? → A: A factory constructor is called like a constructor and can return a subtype or cached instance. A static method can have any name and return type, including Future.
  • Q: Factory vs Factory Method? → A: A simple factory is one function with a switch. Factory Method lets subclasses decide via an overridden method.

مصدر: Dart factory constructors

6 Repository

1. ما هو؟
طبقة بتدي باقي الـ app API بلغة الـ business (getEmployee, submitEvaluation) وبتخبي منين البيانات (API، cache، local) وإزاي بتتحول.

2. ليه اتعمل؟
عشان الـ business logic ما يتربطش بـ database أو API معين، وعشان الـ mapping والـ caching يبقوا في مكان واحد.

3. المشكلة

  • قبل: الـ Cubit بيقرا raw['full_name'] من Firestore.
  • بعد: repo.getEmployee(id) بيرجع Employee.

4. بيشتغل إزاي؟

Cubit → Repository (interface) → RepositoryImpl → DataSource(s) → Firebase/API/Local
  • Data Source: I/O خام.
  • Repository: يجمع + يحول + يقرر cache/source of truth.

5. ليه في Flutter؟

  • Offline-first.
  • Cache.
  • تغيير backend.
  • Testing بـ fake repo.

6. امتى؟

  • مناسب: أكتر من مصدر بيانات، cache، offline، backend ممكن يتغير، محتاج تختبر الـ Cubit.
  • زيادة: app صغير بـ backend واحد ثابت، وفيه service نضيف بيرجع models. الـ repository هيبقى pass-through بس.

7. عيوبه

  • Boilerplate (methods بتنادي methods).
  • لو مفيش interface، نص القيمة بس.
  • خطر إنه يبقى "service تاني بنفس الاسم".

8. Interview

EN: "A repository is the boundary between business logic and data sources. It exposes a domain-level API, hides whether data comes from remote or cache, and owns the mapping. A good repository can combine several data sources, for example a Firestore source, an access-rules check and a user lookup, and verify the write reached the server. Cubits only talk to the repository. Putting repositories behind interfaces lets you unit-test Cubits with fakes."

بالمصري: "طبقة بتخبي منين البيانات، ومن غير interface قيمتها نصها بس."

9. أسئلة متابعة

  • Q: Should a repository return Firestore types? → A: No. It should return app models or entities.
  • Q: One repository per collection or per feature? → A: Per domain concept or aggregate, not per table.
  • Q: Where does caching live? → A: In the repository. The data source just does I/O.

مصادر: Fowler – Repository · Flutter architecture guide

7 MVVM (Architectural Pattern)

1. ما هو؟
تقسيم الـ presentation لـ 3:

  • View: بيعرض.
  • ViewModel: state + logic، وبيعمل expose لـ observable state.
  • Model: البيانات والخدمات.

2. ليه اتعمل؟
عشان الـ UI يبقى "غبي" ويتختبر الـ logic من غير widgets.

3. المشكلة

  • قبل: شاشة 1000 سطر فيها Firestore queries و filtering و setState.
  • بعد: الشاشة بتعرض الـ state، والـ Cubit بيحسبه.

4. بيشتغل إزاي؟

  • الـ View بيبعت events (cubit.search(text)).
  • الـ ViewModel بيحدّث الـ state.
  • الـ View بيعمل observe ويعيد الرسم.

5. ليه في Flutter؟
Flutter الرسمي بيوصي بـ MVVM (Views + ViewModels + Repositories + Services).

6. امتى؟

  • مناسب: تقريباً أي شاشة فيها logic.
  • زيادة: شاشة static (About).

7. عيوبه

  • ViewModel ممكن يبقى ضخم (Cubit بـ 500+ سطر).
  • Boilerplate للـ state.

8. Interview

EN: "I use MVVM where the Cubit is the ViewModel. The screen only renders state and forwards user actions, and the Cubit owns filtering, ranking and data loading through services. States are immutable with Equatable. A common mistake is keeping a TextEditingController inside a state class. It belongs in the widget, because the ViewModel shouldn't hold UI objects."

بالمصري: "الـ Cubit هو الـ ViewModel، والشاشة بتعرض بس."

9. أسئلة متابعة

  • Q: Is Cubit = MVVM automatically? → A: No. If the screen still does data access or logic, it isn't MVVM.
  • Q: Where do navigation and toasts go? → A: The ViewModel exposes a state or event, and the View performs it in a BlocListener.

مصادر: Flutter – App architecture guide · Fowler – GUI Architectures

8 Strategy

1. ما هو؟
عيلة algorithms، كل واحد في object لوحده بنفس الـ interface، وتقدر تبدّلهم وقت التشغيل.

2. ليه اتعمل؟
عشان if/else الكبير بيتعدّل مع كل حالة جديدة ويكسر الكود القديم.

3. المشكلة

  • قبل: if (method == 'gps') ... else if ('qr') ...
  • بعد: CheckInService(GpsCheckIn())، ولو عايز طريقة جديدة بتعمل class جديد.

4. بيشتغل إزاي؟

  • Strategy interface.
  • Concrete strategies.
  • Context بيمسك strategy ويناديه.

في Dart: الـ strategy ممكن تبقى function (typedef).

5. ليه في Flutter؟

  • Check-in methods.
  • Sorting.
  • Pricing.
  • Validation.
  • Navigation لكل platform.

6. امتى؟

  • مناسب: الحالات بتزيد، أو بتتبدل حسب config أو platform.
  • زيادة: 2–3 حالات ثابتة. switch على enum أوضح.

7. عيوبه

  • Classes أكتر.
  • الـ client لازم يعرف يختار أنهي strategy.
  • Static hooks صعب تختبرها.

8. Interview

EN: "Strategy encapsulates interchangeable algorithms behind one interface. In Dart a function type works as a lightweight strategy. For example, screens can call an AppNavigator.pushNamed that uses Navigator on mobile, while a web build plugs in a go_router-based function at startup. Better still, inject the strategy instead of storing it in a static field."

بالمصري: "بدّل الـ algorithm من غير ما تلمس اللي بيستخدمه."

9. أسئلة متابعة

  • Q: Strategy vs State? → A: See comparison 8 in Part 2.
  • Q: How does it relate to Open/Closed? → A: You add a new strategy class without modifying existing code.

مصدر: Strategy

9 Adapter

1. ما هو؟
Wrapper بيخلي class بـ interface مختلف يشتغل مع كود متوقع interface تاني.

2. ليه اتعمل؟
عشان تستخدم كود موجود (library، API قديم) من غير ما تعدله ومن غير ما تعدل الكود بتاعك.

3. المشكلة

  • قبل: كل شاشة بتحول ساعات Odoo لأيام.
  • بعد: OdooLeaveBalanceAdapter implements LeaveBalanceProvider.

4. بيشتغل إزاي؟

  • Target = الـ interface بتاعك.
  • Adaptee = الـ class الغريب.
  • Adapter = بيعمل implement للـ target وبيفوّض للـ adaptee مع الترجمة.

5. ليه في Flutter؟

  • REST/ERP APIs.
  • Plugins مختلفة لكل platform.
  • مكتبات navigation مختلفة.

6. امتى؟

  • مناسب: كود ما تقدرش تعدله، و interface مختلف.
  • زيادة: لو تقدر تعدل الـ class نفسه بسهولة.

7. عيوبه

  • طبقة زيادة.
  • Adapters كتير = تعقيد.
  • ترجمة ناقصة (_ => null بتبلع routes مش معروفة بصمت).

8. Interview

EN: "An Adapter converts one interface into another that the client expects. For example, a web app that reuses mobile screens built with named routes can use a route bridge that translates those names into go_router paths, plus a small host widget that turns go_router's extra into the route arguments the screens expect. The screens don't need any changes."

بالمصري: "مترجم بين اتنين بيتكلموا لغات مختلفة."

9. أسئلة متابعة

  • Q: Object adapter vs class adapter? → A: An object adapter uses composition, which is the common choice in Dart. A class adapter uses inheritance from both, which Dart doesn't support for multiple classes.
  • Q: Adapter vs Facade? → A: See comparisons.

مصدر: Adapter

10 Service Locator

1. ما هو؟
Registry مركزي، والـ class بيطلب منه اللي محتاجه بالـ type: locator.get<T>().

2. ليه اتعمل؟
عشان تجيب dependencies من غير ما تمررها في سلسلة constructors طويلة.

3. المشكلة

  • قبل: تمرير service من main لحد شاشة جوه 5 مستويات.
  • بعد: getIt<AuthService>() من أي مكان.

4. بيشتغل إزاي؟

  1. Register عند البداية.
  2. Get وقت الحاجة.

5. ليه في Flutter؟

  • get_it مشهور.
  • مفيد في أماكن مفيهاش BuildContext (background handlers).

6. امتى؟

  • مناسب: الحدود (composition، background isolate، legacy code).
  • زيادة/خطر: جوه business classes.

7. عيوبه

  • Dependencies مخفية.
  • Crash وقت التشغيل لو نسيت register (في Flutter: ProviderNotFoundException، بتحصل مثلاً لما شاشة تتعرض في shell مش عامل provide للـ cubit بتاعها).
  • Tests محتاجة reset للـ registry.

8. Interview

EN: "A Service Locator is a registry that classes query for dependencies. It's convenient but hides dependencies and fails at runtime. In Flutter, context.read<T>() acts as a locator, so keep it at the edge, inside each screen's static builder, and then inject into the Cubit's constructor. A classic failure is ProviderNotFoundException when a shell hosts a screen without providing its Cubit's dependencies, which is exactly the locator downside."

بالمصري: "الـ class بيسحب بدل ما يستلم. استخدمه على الأطراف بس."

9. أسئلة متابعة

  • Q: Is get_it bad? → A: No. Register in one place and resolve at the edges, or combine it with constructor injection.
  • Q: How do you test code using get_it? → A: getIt.reset() and register fakes in setUp.

مصادر: Fowler – Service Locator vs DI · get_it

11 Command

1. ما هو؟
تحويل طلب/عملية لـ object، فتقدر تخزنه في queue أو تأجله أو تعيده أو تلغيه (undo) أو تسجله.

2. ليه اتعمل؟
عشان تفصل "مين بيطلب" عن "إمتى وإزاي يتنفذ".

3. المشكلة

  • قبل: check-in والنت فاصل، فالطلب بيضيع.
  • بعد: CheckInCommand في queue، ويتنفذ لما النت يرجع.

4. بيشتغل إزاي؟

  • Command فيه execute() (واختياري undo()).
  • Invoker (queue) بيخزن وينفذ.

في Dart ممكن الـ command يبقى closure.

5. ليه في Flutter؟

  • Offline queues.
  • Undo/redo.
  • Flutter docs بيستخدمه في الـ ViewModels عشان كل action يبقى ليه running/error state.

6. امتى؟

  • مناسب: retry/offline، undo، audit log، actions محتاجة loading state مستقل.
  • زيادة: لو الـ backend بيعمل queue لوحده.

7. عيوبه

  • Classes أكتر.
  • Idempotency: نفس الـ command ممكن يتنفذ مرتين بعد reconnect.
  • In-memory queue بيضيع لو الـ app اتقفل.

8. Interview

EN: "Command turns an action into an object, so it can be queued, retried or undone. A network layer can keep a request queue that stores closures while offline and flushes them on reconnect. But if your data goes through Firestore, it already queues writes offline, so a second queue is duplication. Don't rebuild what the platform gives you."

بالمصري: "العملية بقت object تقدر تأجلها. ومش هعمل queue لو Firestore عامله أصلاً."

9. أسئلة متابعة

  • Q: How do you avoid duplicate execution after a retry? → A: Give each command an id and have the server dedupe on it (idempotency key).
  • Q: How do you persist the queue? → A: Store serializable command data (not closures) locally, e.g. in Hive or SQLite.

مصادر: Command · Flutter – Command pattern

الجزء التاني — المقارنات

1 Singleton vs Factory

Singleton Factory
الفرق الأساسي بيضمن عدد النسخ (واحدة) بيقرر إزاي/أنهي نسخة تتعمل
بيحل مورد مشترك واحد منطق إنشاء متكرر أو معقد
امتى الأول cache، logger، connectivity monitor —
امتى التاني — parsing، اختيار نوع، fallback

مثال Flutter:

  • LocalStorage.instance
  • UserProfileModel.fromFirestore(doc)

تميز بينهم في الكود:

  • private constructor + static instance = Singleton.
  • factory X.fromY أو static X create(...) بيرجع objects مختلفة = Factory.

ممكن يتجمعوا: factory X() => _instance; (factory بيرجّع singleton).

سؤال: "Can a factory return a singleton?"

Yes, a Dart factory constructor can return a cached instance. That's a common way to implement a singleton.

2 Factory vs Abstract Factory

Factory (Simple / Method) Abstract Factory
الفرق الأساسي بيعمل منتج واحد بيعمل عيلة منتجات لازم تتماشى مع بعض
بيحل منطق الإنشاء التناسق بين منتجات مرتبطة
امتى الأول notification حسب النوع —
امتى التاني — MaterialUiFactory / CupertinoUiFactory بيعملوا Button + Dialog + Switch

تميز بينهم: Abstract Factory = interface فيه أكتر من createX()، وليه أكتر من implementation.

سؤال: "When would you use Abstract Factory in Flutter?"

Rarely. Platform widget families or white-label apps, where each brand needs a matching set of services.

3 Repository vs Service

Repository Service
الفرق الأساسي بيمثل البيانات (collection-like) بلغة الـ domain بيعمل عملية أو بيلف SDK
بيحل فصل الـ business عن مصادر البيانات + cache + mapping تجميع operation (send notification, auth)
امتى الأول EmployeeRepository.getEmployee —
امتى التاني — NotificationService.send، AuthService

غلطة شائعة: class واحد اسمه XService بيعمل الاتنين مع بعض (data access + mapping).

في Flutter docs: Services = أدنى طبقة بتلف APIs، و Repositories فوقيها.

تميز بينهم:

  • Methods زي get/watch/save بترجع models = repository.
  • Methods بأفعال (send, upload, signIn) = service.

سؤال: "A class that reads Firestore and returns models — repository or service?"

Both. It's a data source plus a repository without an interface. I'd split raw Firestore access from mapping and caching.

4 Repository vs Data Source

Repository Data Source
الفرق الأساسي بيجمع مصادر ويقرر مصدر واحد، I/O خام
بيحل source of truth، cache، mapping التعامل مع backend معين
امتى الأول دايماً قدام الـ Cubit —
امتى التاني — RemoteAttendanceDataSource (Firestore)، LocalAttendanceDataSource (Hive)

تميز بينهم:

  • Data source بيرجع maps/DTOs.
  • Repository بيرجع models وبيمسك أكتر من data source.

سؤال: "Why not let the Cubit use the data source directly?"

Then the Cubit would decide caching and mapping, and changing the backend would touch every Cubit.

5 Dependency Injection vs Service Locator

DI Service Locator
الفرق الأساسي الـ dependency بتتدفع للـ class الـ class بيسحبها
باينة؟ أيوه في الـ constructor لأ، جوه الـ methods
الخطأ امتى؟ Compile time Runtime
امتى الأول business classes، Cubits —
امتى التاني — الأطراف، background handlers

مثال:

  • ProfileCubit(EmployeeRepository repo)
  • getIt<EmployeeRepository>()

تميز بينهم: دوّر على .get<، أو context.read جوه logic، أو X.instance جوه methods.

سؤال: "Is Provider DI or a Service Locator?"

The tree-scoped providers are DI-like. context.read is a lookup, so I keep it at the edge and inject into the Cubit.

6 MVC vs MVP vs MVVM

MVC MVP MVVM
الوسيط Controller Presenter ViewModel
العلاقة بالـ View Controller بيستقبل input ويحدّث Model، والـ View بتقرا Model Presenter ماسك reference لـ View interface وبيقوله "اعرض كذا" ViewModel ما يعرفش الـ View. الـ View بيعمل observe
Testing صعب Presenter سهل (mock view) ViewModel سهل
في Flutter نادر نادر الأشهر (Cubit/ChangeNotifier)

تميز بينهم:

  • لو الوسيط بينادي view.showLoading() = MVP.
  • لو بيعمل emit(state) والـ View بيسمع = MVVM.

سؤال: "Which does BLoC resemble?"

MVVM. The Bloc or Cubit exposes a state stream that the view observes, and it holds no reference to the view.

7 Observer vs Stream

Observer Stream
إيه هو Pattern (فكرة) Implementation في Dart للفكرة دي (async)
فيه زيادة — async، errors، done، operators (map, where)، backpressure
امتى الأول (بشكل يدوي) listeners بسيطة sync: ChangeNotifier, ValueNotifier —
امتى التاني — events متتالية async: Firestore، websocket، Bloc

تميز بينهم:

  • addListener / notifyListeners = observer كلاسيكي sync.
  • Stream / listen = نسخة async.

سؤال: "ChangeNotifier vs Stream?"

ChangeNotifier is synchronous with no payload, so listeners read state. A Stream carries values and errors asynchronously and supports transformations.

8 Strategy vs State

Strategy State
مين بيبدل الـ client من برة بيختار الـ object نفسه بيبدل الـ state بعد كل action
الـ strategies تعرف بعض؟ لأ أيوه، كل state بيرجّع الـ state اللي بعده
بيحل algorithms بديلة سلوك بيتغير حسب الحالة + transitions
مثال GPS/QR/Wi-Fi check-in Leave: Draft → Submitted → Approved

تميز بينهم:

  • لو methods بترجّع state جديد = State.
  • لو حد من برة بيعمل setStrategy = Strategy.

سؤال: "Both look the same in UML. What's the difference?"

Intent and who drives the switch. In Strategy, the client picks the algorithm. In State, transitions happen internally as a result of actions.

9 Builder vs Factory

Builder Factory
الإنشاء خطوات متعددة، وبعدين build() call واحدة
بيحل objects بـ parts كتير اختيارية + validation اختيار نوع/منطق إنشاء
مثال ReportRequestBuilder().between().dept().build() AppNotification.forKind(kind)

ملاحظة Dart: named parameters بتقلل الحاجة للـ Builder. و static Widget builder(context) على الشاشات = factory، مش Builder.

تميز بينهم: chain من methods بترجع this وتنتهي بـ build() = Builder.

سؤال: "Why is Builder less common in Dart than Java?"

Named and optional parameters with defaults solve telescoping constructors.

10 Architecture vs Design Pattern

Architecture Design Pattern
النطاق التطبيق كله classes قليلة
بيحدد layers، اتجاه الـ dependencies، boundaries تفاعل objects لحل مشكلة محلية
أمثلة MVVM، Clean، Layered Strategy، Adapter، Observer
مثال Flutter Feature-first layered + MVVM presentation Facade، Observer، Singleton… جوه الـ layers

تميز بينهم:

  • لو بتتكلم عن "مين يعرف مين بين الفولدرات/الـ packages" = architecture.
  • لو عن "إزاي الـ 3 classes دول بيتعاملوا" = pattern.

سؤال: "Describe your project's architecture without naming patterns."

Screens render state from Cubits. Cubits hold UI logic and call service classes that wrap Firebase. All services are created in one composition root and injected.

الجزء التالت — أنماط لسه هتتعلمها (مختصر)

Clean Architecture (Architectural)

  • المشكلة: الـ business logic مربوط بـ Firebase والـ UI.
  • الفكرة: Domain (entities + use cases + repo interfaces) في النص. Data و Presentation بيعتمدوا عليه. Dependency Rule: الأسهم بتشاور للداخل.
  • علامة إنك محتاجه: core/ بيستورد من features/، أو فيه package cycle.
  • امتى زيادة: app صغير. use case بيعمل return repo.x() بس.
  • مصدر: The Clean Architecture

Result type (Error handling)

  • المشكلة: الـ signature بيكدب، Future<T> ممكن يرمي.
  • الفكرة: sealed class Result<T> (Ok / Err) + switch exhaustive.
  • الخطوة الطبيعية: لو عندك Failure classes، الـ Result هو اللي بعدها.
  • مصدر: Flutter – Result

Decorator (GoF – Structural)

  • المشكلة: عايز تضيف cache/log/retry من غير ما تعدل الـ class.
  • الفكرة: wrapper بنفس الـ interface بيلف التاني.
  • في Flutter: widget wrappers هي نفس الفكرة على مستوى الـ UI.
  • مثال: 10_decorator_cached_repository.dart
  • مصدر: Decorator

State (GoF – Behavioral)

  • المشكلة: if (status == ...) في كل method.
  • الفكرة: كل state object بيقرر الـ actions والـ transitions.
  • ملاحظة: enum (idle/loading/success/error) كفاية للـ UI status البسيط.
  • مثال: 12_state_leave_request.dart
  • مصدر: State

Builder (GoF – Creational)

  • المشكلة: constructor بـ parameters كتير.
  • الفكرة: بناء خطوة بخطوة + build().
  • ملاحظة: static Widget builder(context) = factory، مش Builder.
  • مثال: 13_builder_report_request.dart
  • مصدر: Builder

Factory Method (GoF – Creational)

  • المشكلة: الـ superclass عنده algorithm، بس نوع الـ object اللي بيتعمل جواه يختلف حسب الـ subclass.
  • الفكرة: abstract Widget createButton(); والـ subclasses بتعمل override.
  • ملاحظة: نادر في Flutter apps.
  • مصدر: Factory Method

Abstract Factory (GoF – Creational)

  • المشكلة: عيلة objects لازم تتماشى مع بعض.
  • ملاحظة: نادر في Flutter.
  • مصدر: Abstract Factory

Prototype (GoF – Creational)

  • المشكلة: تعمل نسخة من object من غير ما تعرف الـ class بتاعه بالظبط.
  • في Dart: copyWith شبهه، بس مش polymorphic.
  • مصدر: Prototype

Chain of Responsibility (bonus)

  • الفكرة: الطلب بيعدي على سلسلة handlers، وكل واحد يكمّل (next) أو يوقف (reject).
  • في Flutter: Dio interceptors (interceptor بيعمل handler.reject لو offline، وإلا handler.next).
  • مصدر: Chain of Responsibility
